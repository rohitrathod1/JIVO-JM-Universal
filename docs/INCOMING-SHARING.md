# Incoming sharing

The `/share` route receives external text, links and files for explicit review. Nothing sends automatically. The person sees the current account, previews the files, edits the caption and selects up to five unlocked conversations where the server permits sending. File destinations must additionally permit attachments.

Android uses Expo SDK 58's experimental incoming-sharing API, configured through the existing `expo-sharing` plugin. `+native-intent.ts` routes the `expo-sharing` host to `/share`. The adapter reads raw payloads, resolving only a batch consisting entirely of local file/content URIs. Shared web URLs remain text; they are never fetched to construct previews. Mixed text/file shares use local file inspection. Protected, chunked SecureStore metadata binds a reviewed share and its retry plan to its account. An existing unexpired review keeps its original files, recipients and upload/message IDs even when another intent replaces the OS payload or the OS slot disappears after restart. Completing/discarding the old review clears only its matching raw payload; a newer payload can then be reviewed. Expo exposes one raw slot, so this does not promise a queue of every intervening intent. Actual file access still depends on the provider's URI permissions.

For installed supporting browsers, `manifest.webmanifest` advertises a multipart `/share-target`. The service worker stores one pending intake in a separate IndexedDB database (`jm-incoming-share-v1`), then opens review. This is separate from the public static Cache Storage. Intake is capped at ten files, 50 MB total and 4000 text characters; larger files can use the existing chat attachment picker. Records expire logically after ten minutes and are removed when next inspected or replaced by a fresh intake. An existing unexpired share is never overwritten. Browser storage can be evicted, so it is not a permanent archive.

Before the first network mutation, the selected destinations, caption, message client IDs and individual upload idempotency keys are saved durably. Each destination gets its own uploaded copy. Retry retains these IDs, skips confirmed completed destinations and continues the remaining plan after reload. A second tab cannot replace a committed plan with different recipients or IDs. The UI freezes caption/recipients after the first attempt to avoid changing the meaning of an uncertain send. Cancellation aborts pending work; a server-committed message may still have reached its destination and cannot be recalled by this screen.

Confirmed logout/session loss clears intake and retry state and aborts active sends. A browser boundary counter prevents an in-flight service-worker POST from recreating a discarded share after that boundary. Anonymous incoming shares survive initial sign-in for review; account-bound data cannot be read under another account. Each upload/send revalidates `/me/` under the existing shared-session lock, and conversations are rechecked before delivery. Existing server-side idempotency and account-binding limitations remain unchanged; no backend API or schema was modified.

Validation:

- `npx.cmd vitest run src/modules/sharing/sharing.test.ts src/modules/sharing/storage.native.test.ts`: 19 passing cases for input limits, locked/capability gates, safe native URL handling, per-chat upload IDs, durable retry, cancellation, account boundaries and native intent replacement/clear races.
- `scripts/share-ui.cjs`: mocked authenticated browser flow for real IndexedDB review, two destinations, partial failure, reload/retry, expired/other-account isolation. Invoked by the root harness; consult its current report for actual execution status.
- `npm.cmd run test:pwa`: production service-worker multipart intake, separate storage, overwrite rejection and oversized-input rejection, alongside shell/cache/update checks. Rebuild before running.

iOS incoming sharing is disabled because bundle/app-group identifiers and signing are not supplied. Native receiving remains experimental in Expo. A synthetic Android ACTION_SEND text intent opened the explicit review screen on the continuation APK and was discarded without sending. Multiple files, provider permission lifetime, process termination and physical OS pickers still need device checks; browser fixtures do not prove those integrations. This does not provide closed-app background message delivery.

References: [Expo SDK 58 Sharing](https://docs.expo.dev/versions/v58.0.0/sdk/sharing/), original read-only frontend `SharePage.tsx` and `share.ts`.
