# Native passkey feasibility - JIVO-063

Assessment only. Native passkeys are not implemented or validated. No passkey bridge package, entitlement, domain association, server setting, credential or build was changed. The separate vault-export dependencies are described below.

The web adapter in `src/core/auth/security.web.ts` already uses existing server challenges and submits WebAuthn credential JSON for login, step-up and enrollment. The native adapter deliberately reports unsupported and permits only server-offered alternatives. Browser APIs cannot provide native Credential Manager / AuthenticationServices support by themselves.

A future native adapter can preserve these existing endpoint payloads: request server options, invoke the platform credential API, serialize its response as the existing credential JSON, and submit the unchanged flow identifier. It must handle cancellation, unavailable providers, session replacement, base64url serialization and server errors. It must never construct successful verification locally, substitute a web origin, or bypass challenge/origin checks.

Android requires a Credential Manager bridge and a valid Digital Asset Links association for the real app identity and signing certificate. Its returned credential origin must be accepted by the existing server. Compatibility is unverified; an origin mismatch must be reported to the owner without changing backend settings. See [Android passkey creation](https://developer.android.com/identity/passkeys/create-passkeys) and [Credential Manager prerequisites](https://developer.android.com/identity/credential-manager/prerequisites).

iOS requires an AuthenticationServices bridge and the associated domain's webcredentials service. Real app identity/entitlement and the matching website association must be verified. See [Apple Supporting passkeys](https://developer.apple.com/documentation/authenticationservices/supporting-passkeys) and [Apple Meet passkeys](https://developer.apple.com/videos/play/wwdc2022/10092/).

Current restrictions prevent configuring domain/server associations, creating credentials, running native builds or contacting the real API. The final native app identities and association state are not verified. Adding an untested dependency or writing a success-looking adapter would not establish compatibility. Therefore native passkeys remain explicitly unavailable. An authorized device integration phase needs the chosen identities, an approved non-production server, existing association evidence, compatible native adapter/build checks, and enrollment/login/step-up/cancel/error tests on Android and iOS. No paid service or account creation is proposed here.

# Vault file platform status

Native export is now implemented in source using exact SDK-supported expo-file-system 58.0.10 and expo-sharing 58.0.19. It is tested with synthetic in-memory filesystem/sharing mocks only. No native share sheet, real file export, build or device validation has run. See Expo's [Sharing API](https://docs.expo.dev/versions/latest/sdk/sharing/) and [FileSystem API](https://docs.expo.dev/versions/latest/sdk/filesystem/); the installed native source was also inspected.

The user must explicitly confirm export after seeing the decrypted-copy warning. The existing authenticated POST download still uses cookie/CSRF transport and server step-up. The adapter supports non-empty native exports up to 20 MiB to bound base64 conversion; larger files require the web client. Filenames receive an export- prefix, are restricted to bounded ASCII characters and cannot create paths. Each export uses a UUID directory inside the private app cache's dedicated jivo-vault-exports directory. No document-directory copy or remote upload fallback is used.

Only one export can stage at a time. Before staging, old owned cache files are removed and sharing availability and request validity are checked. The temporary file is removed after share completion/cancellation/failure. A two-minute deadline cancels stuck work when JavaScript can run; foreground resumption checks the deadline again. Startup, session loss and explicit cancellation remove owned staging. Cleanup errors are visible and future export fails closed until cleanup succeeds. The tests cover unavailable sharing, focus/session loss during decode, cancellation, partial writes, stuck shares, suspended timers, concurrent requests and cleanup failures. Files outside the dedicated directory are untouched in the synthetic adapter tests.

On iOS the adapter deliberately supplies no MIME/UTI override, avoiding the inspected Expo implementation's extra type-adjustment staging copy. Android shares an app-owned content URI with read access through Expo's FileProvider. Actual OS handoff timing, receiver compatibility, filesystem protections and permission revocation are not validated. Cleanup immediately after the share API returns can cause a receiver that reads later to fail; the app does not retain plaintext longer as a workaround. Device tests must verify intended receivers. The API does not prove that the receiver saved the file, so the UI makes no delivery-success claim.

A killed or suspended process cannot guarantee immediate JavaScript cleanup. An interrupted temporary cache file can remain until the next launch/foreground cleanup or OS cache removal. Logical deletion is not a claim of physical secure erasure. Copies intentionally saved by a recipient app are outside this app's control; users must protect and remove those copies. These are material limits of native export, not validated security guarantees.

Shared file UI implements raw upload/progress/cancel, temporary preview, rename/delete and permission checks. Download and preview now receive AbortSignals: blur/unmount and explicit cancellation abort them, including a pending step-up prompt. Downloads have a 120-second request timeout; previews retain the normal transport timeout. A late cancelled response must not create a Blob URL or stage a native file. JSON Blob error bodies are decoded before step-up while preserving retry/session guards. Preview text uses server expiry capped at 60 seconds and disappears on background. Web download uses a temporary Blob URL revoked after save initiation.

Vault-file upload (pickVaultFile) uses the document picker without an app-requested cache copy and reads only local provider URIs into a Blob. Messenger/profile pickDocument instead copies the selected provider file into a uniquely owned cache directory and returns a disposal handle; replacement/cancel/success/unmount and stale results dispose that owned copy. Provider URI access, memory behavior and authenticated upload remain device-unverified; provider-managed caching cannot be guaranteed absent. No backend or domain configuration was changed.

## Capture, image and outbox source assessment (2026-10-20T11:17:26.969Z)

Native capture adapters use the existing Expo audio/image-picker modules plus exact SDK-compatible expo-contacts 58.0.8; image transforms use expo-image-manipulator 58.0.15. app.json declares action-specific microphone/camera/contact permission text, disables background recording/playback, and blocks Android WRITE_CONTACTS. Native generated projects are stale and were not rebuilt. These are declarations and source, not observed OS behavior.

Camera/contact/voice actions begin only after an explicit button. Captures are reviewed before uploading to the existing scanner endpoint; adding an attachment does not send the message. Contact selection reads one selected contact, never bulk syncs or writes contacts. Voice auto-stops after 60 seconds. Cancellation/background invalidates results and attempts owned-cache cleanup. Temporary outputs are cache files and can remain after process death or cleanup failure; deletion is not secure erasure. OS/provider caching and native AppState transitions around system pickers need device checks. No actual microphone/camera/contact permission or data access was performed.

Document selection copies only the chosen local provider file into a uniquely owned cache directory. Replacement, cancellation, successful upload and unmount dispose ownership handles. Late selections are disposed after generation invalidation. Image manipulation returns owned cache output and releases native handles; metadata failure cleanup has synthetic tests. Native crop/rotate/flip, zoom and PNG conversion are implemented. The later frame adapter described below adds native frame source; device rendering remains unverified. Editing animated GIFs flattens them. Native authenticated upload and format decoding are unverified.

Native outbox is intentionally memory-only. Durable native drafts require a reviewed account-bound encrypted storage/key lifecycle, logout destruction, backup behavior and process/device tests. SecureStore alone is not a complete durable message queue. No new plaintext native message store, credentials persistence, custom cryptography or pretend secure fallback was added. Pending native messages are lost on process exit.

Browser outbox uses transactional IndexedDB entries/tombstones and Web Locks, revalidates authenticated identity before send, and freezes other tabs on this client's auth changes. Synthetic two-tab shared-cookie tests pass; real backend integration and atomic protection against unrelated clients changing cookies outside the lock are not established. Native passkey and vault export caveats above remain unchanged.

## Messenger export, frame rendering and review fixes (2026-10-21T05:40:43.143Z)

Messenger exports reuse the tested export controller with a separate jivo-message-exports cache root, explicit confirmation and fresh message-window access. Only ready attachments with supported /api/jm/ paths are downloaded through existing authenticated transport, with AbortSignal/timeout and validity checks. Export cancellation, access loss, session loss and unmount invalidate work. The 20 MiB limit, two-minute deadline, interrupted-process cleanup, receiver-read timing and non-secure-erasure caveats of vault export also apply. Tests use synthetic data only.

The native frame adapter uses exact Expo-bundled react-native-view-shot 6.1.1. Only the selected, edited image view is captured after Apply; it does not capture the device screen or other apps. It waits for image load/layout, returns a local temporary PNG, releases late/cancelled outputs and transfers an explicit disposal handle. Metadata/late-result cleanup uses mocks. The input image copy is disposed after the frame job. Actual Android/iOS rendering, alpha/corners, resolution, tmpfile location/lifetime and releaseCapture behavior are unverified; a crash or cleanup error can leave a temporary image until library/OS cleanup. Native circle frames require square crop. Native view rasterization may resample from the bounded preview and is not exact original canvas output.

Camera/contact adapters now check action validity before and after permission requests, after picker completion and after detail retrieval. A cancelled/backgrounded action cannot open a subsequent native surface or read selected-contact details after it becomes invalid. Voice cleanup attempts deletion, recorder release and audio-mode reset independently even when another step fails; errors are aggregated. Dependency-mock tests verify deferred permissions and deletion/release failures, not real permission APIs.

Cross-tab coordination only covers cooperating same-origin clients. Server-side expected-principal binding is a prerequisite for preventing a different client/origin from replacing the session between identity check and message POST. No server/domain settings were changed.

## Clipboard and app-lock review follow-up

Explicit web secret copy is available with synthetic coverage; native copy and automatic OS clipboard clearing are unavailable. No clipboard dependency was added, no actual clipboard access ran, and no empty clipboard write occurs. CLIPBOARD-LIFECYCLE.md records the atomic-ownership limitation and manual checks.

Web app-lock storage read errors now fail closed instead of being interpreted as disabled. Cancel, background, model generation changes and unmount invalidate the entire status/options/credential attempt and clear password state. Only a current foreground attempt may unlock. This deliberately strengthens the current reference behavior. Native app lock remains unavailable.
